# Project: TP-Link TL-WR840N V6.20 / V6.2 with XMC XM25QH32DHIG

## Goal
Investigate and fix boot failure on the TP-Link TL-WR840N hardware revision 00000007 when fitted with XMC XM25QH32DHIG SPI-NOR flash (32 Mbit / 4 MiB; reported JEDEC ID 0x204016). The router currently fails to boot after installing a custom OpenWrt 19.07.10 build. The WAN LED blinks red continuously. The device can be restored to stock TP-Link firmware using the previously tested recovery process.

## Known-good comparison
A separate TL-WR840N V6.2 with EON EN25QH32 flash boots OpenWrt 19.07.10, Linux 4.14.275. Its observed MTD layout:
- mtd0 0x00010000 `boot`
- mtd1 0x003e0000 `firmware`
- mtd2 0x00144daf `kernel` (subpartition)
- mtd3 0x0029b250 `rootfs` (subpartition)
- mtd4 0x00080000 `rootfs_data`
- mtd5 0x00010000 `factory`
The working device reports `en25qh32 (4096 Kbytes)` in dmesg. Do not assume the XMC chip is a drop-in equivalent merely because capacity and JEDEC ID are known.

## Source and current patch
The source archive is `source/openwrt-19.07-tl-wr840n-v6.x-main.zip`.
It contains `target/linux/generic/pending-4.14/480-mtd-spi-nor-add-xmc-xm25qh32d.patch`, which adds:
`{ "XM25QH32D", INFO(0x204016, 0, 64 * 1024, 64, SECT_4K) },`
The patch claims 64 x 64-KiB sectors and 4-KiB erase support. It is intended to follow patch 478 for other XMC parts. Verify actual patch application order and all interactions; do not trust the patch description alone.

## Critical safety rules
1. FIRST TASK IS READ-ONLY AUDIT. Do not edit source, generate a new firmware, recommend flashing, or invoke any flash/recovery command until the audit is complete and findings are presented.
2. Never assume that a successful compile proves hardware boot compatibility.
3. Never change flash geometry, MTD partition boundaries, bootloader offsets, image headers, or device profile without evidence from source, stock firmware layout, and known-good device data.
4. Do not invent register values, status bits, SFDP capabilities, QE requirements, erase opcodes, dummy cycles, or chip timing. Cite the exact datasheet or source-code evidence for each claim. If missing, mark UNKNOWN and request the datasheet/log.
5. Preserve the stock firmware recovery path. Never instruct flashing the `sysupgrade.bin` from stock firmware. Do not flash anything during this project unless the user explicitly authorizes a separately reviewed test plan.
6. Keep all work in a new Git branch and make small reviewable commits. Do not overwrite original files.
7. Treat OpenWrt 19.07.10 as a legacy/EOL baseline selected for compatibility investigation, not a security recommendation.

## Required investigation
A. Identify exact source revision and target profile. Confirm the profile symbol generated by this source tree (note that the human-readable profile name contains `v6.2`; Kconfig symbols may normalize punctuation).
B. Trace the patch series in exact lexical/application order, especially patches 478, 479, both 480-prefixed patches, and 481. Verify whether the XMC patch applies cleanly and whether it is actually present in the prepared kernel source used for compilation.
C. Inspect Linux 4.14.275 `spi-nor.c` structure and `struct flash_info` / `INFO()` semantics. Compare XMC entry against the EN25QH32 entry and other supported chips. Verify all relevant capabilities: read modes, address width, erase types, page size, protection behavior, status-register handling, and SFDP fallback, using code and reliable datasheet evidence only.
D. Verify the device tree, SPI controller configuration, flash node, partition map, image recipe, image size, and bootloader expectations for TL-WR840N V6.2. Compare against stock image and the working EN25QH32 OpenWrt device.
E. Inspect build workflow for errors: source archive extraction, config symbol, feeds, patch application, kernel config, build outputs, artifact naming and hashes. Flag any mismatch rather than silently fixing it.
F. Explain which evidence is still needed from the failed XMC device (serial boot log is preferred; LED and ping observations are weaker evidence). Do not request SSH to stock firmware as if it were OpenWrt.

## Output format for first task
1. Executive summary: most likely causes ranked, clearly labeled as hypotheses.
2. Evidence table: claim, exact file/line or log, what it proves, what it does not prove.
3. Patch audit: applied/not applied, exact order, resulting source excerpt, compile inclusion evidence.
4. Hardware/partition/image audit.
5. Build workflow audit.
6. Missing evidence checklist.
7. Safe next step. No firmware flashing instructions in the first response.
